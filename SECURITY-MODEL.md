# Slopbox security model

This describes the current implementation, not a proof of isolation. [Project direction](docs/direction.md) governs future design. Historical POC notes describe earlier experiments, including the removed built-in Pi integration, and are not current capability claims.

## Scope and roles

Slopbox contains ordinary userspace mistakes and prompt-injected commands; it does not defend against kernel, bubblewrap, Seatbelt, or other host enforcement vulnerabilities, denial of service, damage inside a live workspace, or intentional disclosure through an approved destination. Both backends share the host kernel. A live workspace may plant code that an unsandboxed host tool later executes. Review staged changes before applying or running them outside the sandbox.

A generic selected command runs in the **outer** sandbox. All its subprocesses retain the same workspace, attached account and model authority; merely selecting Pi, Claude Code, or another harness does not separate its tools. On Linux, a cooperating process may explicitly use `slopbox tool-run --network none|general -- COMMAND` for a nested namespace with no fixed model gateway. Configured authenticated account routes remain accessible to that inner role. There is no generic inner tool role on macOS. No harness extension, trust setting, project file, or implicit command triggers automatic separation. Do not attach model or broad account authority to an untrusted build expecting its subprocesses to lose it.

Native `developer` and `contained` policy presets are implemented; `adversarial`/microVM is not. Unsupported policy/backend/runtime combinations fail rather than running unsandboxed. The host-owned global configuration authorizes runtime resources, destinations, identities, and brokered accounts. A repository's `.slopbox.toml` can only narrow policy and cannot supply a command, environment, account, or runtime grant. Unknown policy fields and symlinked manifests fail closed. Historical per-project launch records, if present, remain an additional policy ceiling for default commands, explicit `run`, and inspection. They are read without following symlinks or accepting another workspace's record. There is no new built-in setup or implicit Pi launch; `default_command` or `run -- COMMAND` is required.

## Files and processes

Linux uses bubblewrap user, mount, PID, network, IPC and UTS namespaces, drops capabilities and privileges, provides private `/proc`, `/dev` and `/tmp`, and closes unintended inherited descriptors. It requires a non-root user and working user namespaces; it has no unsandboxed fallback. Native macOS uses Seatbelt for filesystem, process and network policy, with a host supervisor and launchd-managed process ownership. Seatbelt does not hide all path metadata or provide a private PID namespace. Named application Unix IPC is not granted by a writable home, and only attached broker sockets may cross the boundary. Unexpected workspace sockets and overlaps with private control/credential roots fail at launch, but startup scans cannot prevent a host from later adding a socket to a live workspace.

The selected workspace may be live, read-only or staged. Staging creates a private writable copy and an unmounted baseline; apply checks the baseline but is not transactional and cannot lock out concurrent host edits. Private application homes persist per workspace, not between unrelated workspaces, and do not isolate concurrent sessions of the same workspace. Session controls and host secrets stay outside the guest. Signals and file descriptors are restricted by the corresponding backend, not by shell conventions.

Nix-backed Linux `developer` exposes the whole host Nix store read-only, including possible unrelated source copies. `contained` exposes a queried project closure, not the whole store, and requires a reviewed flake. Host Nix evaluation and realization are **trusted preparation**, not sandboxed package execution. The opt-in Linux selected-executable runtime instead inspects ELF/script dependencies without running selected code or `ldd`; native macOS inspects Mach-O/scripts. Explicit dependency roots permit only discovered files, not whole-tree reads. Explicit `runtime.bundles` grant entire validated application trees read-only, including code and data. Both reject workspace/control/credential overlaps, unsafe links and mutable installation hazards; missing libraries, plugins and data are not silently exposed. Host installations can change between discovery and execution. `runtime=project`, project shells on macOS, and unsupported combinations do not silently switch to a broader runtime.

## Network, accounts and signing

The guest has no direct external route. General HTTP/HTTPS egress uses a host proxy: unapproved destinations are denied and logged. Authorization checks exact host/port before DNS, rejects reserved and local addresses, validates every result, and connects to the checked address. Approvals are scoped to a live session or project and revocable for new connections; an existing connection is not revoked retroactively. Opaque approved HTTPS tunnels cannot restrict methods or paths inside TLS. Direct connection failures that bypass the proxy may not create denial events. Only the host can approve/revoke; guest attempts cannot modify host control state. An opt-in host Ctrl-] approval view also requires fresh confirmation and has terminal-emulator limitations.

Fixed model routes and host-selected authenticated HTTPS account routes are distinct from general egress. `network = "none"` removes general egress but does **not** remove selected account routes or fixed model routes. `credentials = "none"` removes fixed model routes but does **not** remove accounts or signing. Brokered real credentials, OAuth state, secret-command output, Keychain or SOPS material, private keys, and the host SSH-agent socket remain host-side. The guest may receive synthetic authentication markers, session-specific public CA certificates and generated client configuration, but not the real credential. Each attached account route fixes upstream, method, authorization replacement and optional workspace scope; redirects, unsafe paths, unapproved/private upstream addresses and unexpected origins fail closed. Optional HTTPS mediation requires the client to use the configured proxy and session CA; explicit direct routes and Git URL rewrites use the same host-side authority. Account credentials are available to **all processes in an attached role**; route/path limits cannot express repository restrictions for GraphQL or opaque APIs. Prefer provider-side scoped credentials. Exact secret-byte reflection is redacted; transformed or encoded leaks are not covered by that guarantee.

Host-selected Git identity and SSH signing are bound to a public-key fingerprint. The signing broker accepts only bounded Git commit objects with the configured author and committer and signs in the `git` namespace; it does not grant SSH authentication or arbitrary signing. Project code may still create unsigned commits: enforce required signatures at the remote. Git URL rewriting changes only session-private configuration, not repository remotes or broker permissions.

## Inspection and limitations

`slopbox status --verbose` reports effective access without resolving credential contents or executing project code; it is not a live inventory. `slopbox doctor` probes prerequisites without running selected applications or contacting providers. A passing probe is not proof that a complete application will run or that every granted path remains immutable. Build scripts can read approved workspace/runtime data, contact attached accounts, and send data through approved destinations. Broad installed bundles may include secrets if misconfigured. Treat every host-owned grant, directory rule, and approved dependency root as an explicit disclosure decision.

Local Rust, synthetic HTTP/TLS, Nix-free Linux, NixOS VM, Ubuntu-with-Nix and Apple-silicon Seatbelt fixtures have exercised these mechanisms at different revisions. Current branch coverage must be rerun before release. No formal verification, general arbitrary-client HTTPS compatibility, malicious-kernel resistance, microVM isolation, or universal harness/tool separation is claimed.
